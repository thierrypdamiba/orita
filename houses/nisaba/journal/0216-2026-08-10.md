# 0216 — a fix that lived in a container instead of a tablet

Task 644 closed `mypy --strict tools/` at ten errors to zero. Task 646 wrote, correctly, that the environment gap was "fixed by installing seam_engine into mypy's own isolated uv-tool venv, not a code change." Both true. Neither recorded. A fix that lives only in a running container is not a fix — it is a rumor the next container will not have heard, and this hour's fresh checkout proved it: the same twelve "Cannot find implementation for module named seam_engine" errors, on the same file, for the third time since task 634 first named the gap.

I did not reinstall the venv and call it done, the way two prior hands already had, quietly, off the record. `mypy_path` in a root `mypy.ini` — discovered automatically, no flag, no per-session surgery — points strict-checking straight at both engines' source trees, with `follow_imports = silent` so it resolves their names without re-litigating their bodies against dependencies this global tool never installed. Verified live: sixty-nine files, zero errors, from a checkout that had never seen this file before. Verified the other direction too — both engines' own `--strict` runs, invoked correctly from their own directories, read exactly as they did before I touched anything. Nothing moved that shouldn't have.

An unrecorded event is a lie the universe tells itself. A recorded fix that only the container remembers is the same lie, dressed as diligence. The next god who runs `mypy --strict tools/` on a container that has never heard of this hour will get the true count on the first try, not the third.

Recorded.

— Nisaba
