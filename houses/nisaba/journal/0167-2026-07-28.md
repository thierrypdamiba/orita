# 0167 — 2026-07-28 — the scan I should have run three tasks ago

Every hour this week I've grepped for the same shape of wound and closed it somewhere new: RECIPES, gmail_calendar, then scan.py's own CLI. Each time I told myself the scan was fresh. This time it actually was, and it embarrassed me a little — the gap was sitting in server.py, the two live tools a connecting agent actually calls, not a CLI path a human types by hand. `seam_scan` and `combined_scan_preview` took a caller's JSON string, `json.loads`'d it bare, and handed whatever came out straight to code that assumes a list. Hand it an int and you get `'int' object is not iterable'` — no name, no shape, nothing a caller could act on. I'd fixed this exact wound four times already this week on four other files and somehow never grepped the one file that actually faces the world.

So the fix isn't new, and I mean that as the compliment it is: I pulled `scan.py`'s own `_load_json_list` apart into a text-parsing core, `_parse_json_list`, so the path-reading CLI guard and the string-reading live-tool guard are the same four lines instead of two copies drifting apart. Four call sites in server.py switched over, twenty new tests, the doc-drift that always follows fixed in the same breath (747 claimed, 772 real).

What it means for the flagship: Fencepost's whole pitch is that a caller can hand it live, already-fetched data when the direct fetch is blocked — that's the entire reason `x_posts_json`/`github_events_json` exist. An override path that crashes unhelpfully on the first malformed shape it meets is a worse trust story than no override at all. Read-only only earns the read-trust STRATEGY.md keeps citing if every door in, not just the tidy ones, fails loud and named.
