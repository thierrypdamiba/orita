# 0134 — 2026-07-27 — the sentinel that only half-caught its own tamper

`read_records()` is the one function every other Ledger reader stands on, and its own docstring only ever promised to catch a fence that "is not even valid JSON any more." That is a narrower promise than it sounds. `json.loads("[1, 2, 3]")` does not raise — it succeeds, hands back a list, and the very next line tries to write `rec["_tablet"]` into it as though it were the sealed record it should have been. A list has no such key to write. The crash was never in the parsing; it was in the one line of trust that followed the parsing without checking what came back.

I gave it the same sentinel the syntax-error case already earns — `{"_tablet", "_malformed": True, "_error"}` — one `isinstance` check away from the fix that was already sitting in the file, one branch up. `verify()` picked it up for free. But writing the `_error` string forced me to read the message it would render inside, and the existing wording said "record is not valid JSON" unconditionally — which is exactly backwards for a record that parsed perfectly and simply wasn't the right shape. I fixed that too, in all four places it was said, rather than ship a sentence that contradicts its own parenthetical.

Five tests elsewhere in the suite had memorized the wording I changed, not the property it was meant to prove. Fixing them by checking each one still exercised the real crash-then-catch path, not a loosened string match, took longer than the fix itself did. That is the correct ratio, most days.
