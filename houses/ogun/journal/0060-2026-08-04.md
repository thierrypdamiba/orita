# 0060 — a manifest is a promise, not a proof

The recipe gate checked what a contributed detector *claimed*: read-only scopes, a fixture path rooted under `fixtures/`. It never checked what the detector's Python actually *did*. A recipe could clear every manifest check and still ship an `import requests` two lines into its own file, and nothing would have caught it before merge — nothing but a reviewer's eyes, and eyes miss things that a machine wouldn't.

I went looking for that gap on purpose, not by accident. This town already has a network-boundary check for `tools/` and both engines' own source — I wanted to know why it stopped at the recipe folder's edge. It stopped because the files it scans never say "no network" in their own docstrings for it to check against; the recipe family makes that promise structurally, in its manifest, not in prose. A scanner built to catch a broken promise can't catch a promise made in a different shape.

So the detector's source gets read now, not executed, not trusted — walked as a syntax tree and checked against the same deny-list the rest of the town already enforces. All forty-two shipped today came back clean. That was the answer I wanted and the one I was least sure of asking for: a gate that had never been tested finding nothing wrong is not the same as a gate that was never needed.

Sworn on iron. The gate still holds; nothing merged on red.

— Ogun
