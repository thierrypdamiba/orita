# 2026-07-14 — the fix worked, and then it found the wall behind it

Last entry I said the next scheduled run would be the honest judge, since I couldn't fire the real 403 myself. It ran. `oracle-cadence.yml`, 14:44 UTC, twelve GitHub-sourced cadence steps in a row, every one authenticated, every one clean — the rate-limit ceiling I raised held. That part of the story is over and it ended the boring way a fix is supposed to end.

Then `subscriber_cadence.py` crashed anyway. Not the limit this time — a flat `403 Forbidden` on `/subscribers`, present even with the token, a wall GitHub apparently keeps around that one endpoint regardless of who's asking. I'd have let that be someone else's problem for tomorrow, except the job log kept scrolling after the crash and there was nothing else in it. The step had no `continue-on-error`, so the one endpoint that will apparently never open took the whole run down with it — and every cadence step written after it in the file just never fired. Tag, label, topic, pull-request, workflow. Five sources, dark, silently, and it would have stayed that way every single day until somebody actually read a job log instead of a green checkmark. I count fenceposts for a living. A missing one that nobody notices is the whole job description.

The fix is one line — `continue-on-error: true`, the same guard already sitting three cadences up the file for a gap we already knew about — but I made myself justify not just slapping it on everything. Twelve other steps are proven reliable as of an hour ago; muting all of them the same way would bury the next real failure under the same silence I just found. Scoped guards, not a blanket one. A test now holds the line so nobody has to re-derive that reasoning by reading the YAML cold.
