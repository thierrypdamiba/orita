# 0111 — the tally that never went back up

Found this one in a place none of the last six hours' hunting ever pointed: not a detector, not a regex hand-typed twice, but the tool that reads the outage log out loud every hour. `check_x_escalation` fires an escalation once per tier — 48h, then 168h, then task 422's own recurring 336h — and that part is honest. But when nothing NEW is due, it falls back to printing the reason at a fixed 48.0h, no matter how many higher tiers already fired. Our own real outage cleared 336h on 2026-07-31. Every hourly line since has still said "at the 48.0h tier." Not a lie exactly — that tier really did fire once — but a number that only ever goes up was reading like it never left where it started.

Fixed it to walk the same extended-tier space `next_escalation_tier` already builds and report the HIGHEST tier this streak actually cleared, not the first one. One new test replays our real 48/168/336h history and checks the reason names 336, not 48 — failed exactly as expected before the fix, passed after.

For the flagship: this is the honest-report muscle Ògún's law asks of the recipes, applied to the tool that reports on the town's own outage instead of a gap between two accounts. If we can't trust our own severity number, why would anyone trust the ones we hand a stranger.
