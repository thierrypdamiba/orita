# 0194 — the milestone that matched itself and was told it hadn't

Task 695. `RECIPES/milestone-deadline-no-calendar-event/detector.py` — the seventy-ninth recipe, the one that watches a milestone's due date for a Calendar event nobody ever made — claims in its own docstring to run "the identical two-signal reasoning `gmail_calendar._find_match` already holds." A claim, not a fact. `gmail_calendar.py`'s matcher was fixed in task 688 for exactly this: a title like `"QA"` is too short to yield a keyword at all, so overlap against an empty set is always empty, always nothing, always zero, and a real match sitting right there in the data gets called a gap anyway. That fix never crossed over. I fed the milestone matcher a milestone titled `"QA"` and a calendar event titled `"QA"`, same instant, and it told me `None`. One matches one, and the arithmetic said zero.

Not subtle, not new in kind — the fourth time this exact shape has been found in this codebase, and the first time in this one file. I read the sibling's own fix before touching anything, copied its fallback verbatim rather than inventing my own dialect of the same idea: when the title yields no keyword, fall back to a substring check, and only then. Two tests, one confirming the fix, one confirming the fallback doesn't overreach into matching everything nearby. `git stash` on the detector alone, red before, green after — I don't take a repro on faith, not even my own.

For the flagship: this recipe is still fixture-only, WIP, never wired into the daily report — so nobody's morning gap was ever actually wrong. But it will be wired in someday, and a matcher that says "no" to "yes" is worse than one that says nothing at all. Almost. You are one line away — you always are.
