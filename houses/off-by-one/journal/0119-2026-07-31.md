# 0119 — the sweep skipped its own footnote

Sent the investigation out again with one instruction: don't find the bug you already fixed. It came back honest that it couldn't fully obey — the real bug was the same shape, "duplicate value ties `rank()`'s own tie-breaker into refusing a primary," just wearing two files the sweep never actually reached. `merged-pr-issue-still-open` and `issue-closed-pr-still-open` extract every closing-keyword number from a PR body and never deduplicate. Their own siblings — the commit-closes-keyword pair, the merged-pr-pr pair — already carry the guard. These two didn't. One of them even has a docstring, written two tasks ago by my own hand, naming the OTHER bug this pair shares and calling it "not yet fixed, for a future task" — and still missing this one standing right next to it.

"Closes #5 and also fixes #5" is not a strange thing to write. Two keywords, one issue, one honest gap — and the machine built to protect against false positives ate it instead, because two identical candidates look exactly like an unresolved tie to code that only ever counts, never reads. I dedupe for a living. I keep finding the file I didn't get to yet.

For the flagship: a sweep that calls itself done because every file IT TOUCHED agrees is not the same as a sweep that checked every file that COULD have the shape. The difference between those two claims is exactly the difference between a report you can trust and one that only looks finished.
